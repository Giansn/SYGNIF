# Real-engine preparation: Unity and Unreal

Preparation for building games in Unity or Unreal, done as working code rather
than notes. This directory is the second half of `gamedev/`: the first half
built a 2D engine from scratch in Python to learn what an engine actually does,
and this half moves that knowledge onto real engines.

Neither editor can be installed in this environment, so the central question was
what can still be made *true* rather than merely written down. The answer shapes
everything here.

## The idea this is built around

**Gameplay logic belongs in a library with no engine reference; the engine layer
is thin adapters.**

That is standard practice, but here it is also what makes the work verifiable.
Unity gameplay code is plain C#; Unreal gameplay code is plain C++. Both compile
and unit-test headlessly *if* they do not reference the engine. So the same
constraint that makes a codebase testable in a studio is the one that makes this
work provable in a container.

```
                    ┌──────────────────────────────────────┐
                    │  GameCore  (C#)   gamecore  (C++)    │
                    │  no UnityEngine   no Unreal headers  │
                    │  fixed timestep · PCG32 RNG ·        │
                    │  swept AABB · tile grid · input      │
                    │  68 tests, 125ms  38 tests, ~10ms    │
                    └───────────────┬──────────────────────┘
                       ┌────────────┴────────────┐
              ┌────────▼────────┐       ┌────────▼─────────┐
              │ Unity adapters  │       │ Unreal adapters  │
              │ MonoBehaviours  │       │ UActorComponents │
              └─────────────────┘       └──────────────────┘
```

## Verify it

```bash
gamedev/realengine/verify.sh
```

```
PASS  Python core (from-scratch engine)          140 tests
PASS  C# core (Unity scripting target)            68 tests, ~150 ms
PASS  Unity adapters (compile against shim)
PASS  C++ core (Unreal build settings)            38 tests, 1542 checks
PASS  Unreal module (compile against shim)
```

## Three results worth pulling out

**The same seed produces the same world in three languages.** PCG32 in Python,
C# and C++ emits a byte-identical stream, asserted in each language's tests
against values generated by the Python original. Neither engine gives you this:
`UnityEngine.Random` is a global the engine itself draws from, and Unreal's
`FRandomStream` is a version-tied LCG.

**Unreal has no fixed gameplay timestep and Unity does.** This is the largest
scheduling difference between them and is easy to miss because both look
similar. Unity's `FixedUpdate` is an accumulator you get for free; Unreal's
`Tick` gets the raw frame delta, and its substepping drives the physics solver
rather than your code. Anything reproducible in Unreal — replays, deterministic
tests, lockstep networking, or a jump that reaches the same height at 30 and
240 fps — needs the accumulator implemented explicitly. It is here as
`USygnifFixedStepComponent`.

**Strict build settings caught real defects, not style nits.** Compiling the
C++ core the way Unreal compiles a game module (`-fno-exceptions -fno-rtti`,
`-Werror` with `-Wconversion` and friends) surfaced implicit `int`→`float`
conversions through the tile grid and a portability bug in a test that depended
on C++'s unspecified argument evaluation order. Both would otherwise have
appeared forty minutes into somebody's engine build.

## What this does not claim

No editor has been run. The shim builds prove the adapters are valid, compiling
code against the correct API surface; they prove nothing about engine behaviour,
and nothing at all about UnrealHeaderTool's reflection, Unity's serialisation,
rendering, assets, audio, or the build pipeline. Those are the majority of what
using an engine involves, and they are laid out as open milestones in
`LEARNING_PATH.md`.
